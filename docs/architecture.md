# Architecture

GovCore is a pnpm-workspace monorepo split into three kinds of packages:

```text
lib/*          reusable, framework-agnostic packages (schema, engines, generated API code)
artifacts/*    deployable apps (the API server, the frontend, a mockup sandbox)
scripts/*      one-off / maintenance scripts
```

## Layering

```text
artifacts/govcore (React/Vite)      artifacts/api-server (Express)
        |  generated hooks                    |  imports engines
        v                                      v
lib/api-client-react   <--openapi.yaml-->  lib/api-spec
        ^ generated by orval                    |
        |                                       v
lib/api-zod             (Zod schemas)      lib/report-engine, lib/search,
                                            lib/integration-engine, lib/queue-utils
                                                      |
                                                      v
                                                  lib/db (Drizzle schema)
```

- **`lib/api-spec/openapi.yaml`** is the source of truth for the API contract. `lib/api-zod` (validation schemas) and `lib/api-client-react` (TanStack Query hooks) are generated from it by Orval -- never hand-edit their `src/generated/` output.
- **`lib/db/src/schema/`** is the source of truth for the database shape, one file per table, re-exported from `index.ts`.
- Business logic ("engines") lives either as a workspace package under `lib/` (`report-engine`, `search`, `integration-engine`, `queue-utils`) when it has no framework dependency, or inside `artifacts/api-server/src/lib/` (`rulesEngine.ts`, `formsEngine.ts`, `notificationEngine.ts`, `documentEngine.ts`, `workflowEngine.ts`, `authorization.ts`) when it's tied to the app's Express/DB wiring.
- **`artifacts/api-server/src/routes/`** is a thin HTTP layer: parse/validate with the generated Zod schemas, call an engine function, serialize the result.
- **`artifacts/govcore/src/pages/`** is organized by feature (one folder per module), with shared primitives in `components/ui/` (shadcn).

## Modules ("Books")

Feature work is organized into numbered "Books," each adding one module plus its schema, engine, routes, frontend pages, and tests:

| Book | Module        | What it owns                                                                                                   |
| ---- | ------------- | -------------------------------------------------------------------------------------------------------------- |
| 05   | Workflows     | Versioned state machines; instances, task inbox, approve/reject, history                                       |
| 06   | Rules         | Versioned boolean condition trees with actions; priority ordering; `/rules/evaluate` sandbox                   |
| 07   | Forms         | Versioned section/field/validation trees; 17 field types; draft/submitted/synced submissions                   |
| 08   | Notifications | Versioned templates; per-recipient delivery queue with backoff and dead-letter                                 |
| 09   | Documents     | Versioned generation from templates; e-signatures; public QR verification                                      |
| 10   | Reports       | Whitelisted data-source catalog; pure spec compiler to parameterized SQL; JSON/CSV output; cron schedule model |

Two cross-cutting engines were added in **Sprint 2A** rather than as a numbered Book, because they serve every module instead of owning a module of their own:

- **Search** (`lib/search`) -- global and entity-scoped search over a denormalized index, permission-filtered, fails closed.
- **Integrations** (`lib/integration-engine`) -- an endpoint registry, HMAC-signed webhook delivery, an append-only event log, and a retry queue with a dead-letter state.

Planned modules (Agriculture, Treasury, Accounting, Budget, HR, Payroll, BPLO, Citizen Portal, Engineering, DRRM, Social Welfare, Health) build on top of this platform layer rather than reimplementing it -- see the README's roadmap table for sequencing.

## Design principles (ADRs)

A handful of decisions are treated as fixed unless explicitly revisited:

- **Definition vs. version split.** Forms, workflows, and rules each have a definition table plus a versioned tree. Published versions are immutable; edits always create a new version, so historical records stay bound to the exact layout/logic that was in force when they were filed. Publishing a new version demotes the previous one to `deprecated` inside the same transaction.
- **Client-supplied temporary keys.** Version-creation endpoints accept a tree whose children reference parents by a request-scoped `key` (not a DB id), resolved server-side inside the transaction -- the same pattern in forms, workflows, and rules.
- **Rules are the shared policy engine.** Forms don't reimplement conditional logic; field visibility, calculated values, and `custom_rule` validations all delegate to `evaluateRules()`.
- **Notifications are event-driven and asynchronous (ADR-0016, ADR-0018).** Modules never call a delivery channel directly -- they create a notification, which fans out to one `notification_queue` row per recipient. `POST /notifications/send` drains due rows, so request latency never depends on a mail/SMS provider being up.
- **Documents are addressed by UUID, not path (ADR-0019).** Storage keys derive from the UUID, so content can move between inline, local disk, NAS, and S3 without invalidating a stored reference or a previously-issued QR code.
- **Signatures bind to a version's content hash, not just a document id**, so regenerating a document leaves the new version correctly unsigned instead of silently inheriting an old approval.
- **Rule isolation.** One rule's evaluation error is logged and skipped rather than aborting the whole batch -- the same failure-isolation pattern the notification and integration retry queues use per-item.
- **Reports only ever touch a whitelisted data source and its declared columns** (`lib/report-engine/src/sources.ts`), and every compiled query is unconditionally tenant-scoped and fully parameterized -- a report spec can never reach an arbitrary table or inject SQL.
- **Shared queue mechanics live in one place.** `@workspace/queue-utils` holds the backoff formula and stale-processing reclaim window used by both the notification queue and the integration retry queue, so the two workers can't drift against each other.
